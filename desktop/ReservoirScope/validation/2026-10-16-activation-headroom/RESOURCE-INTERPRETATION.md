# Resource interpretation — 2026-10-16

Scope: the 64-GiB Apple Silicon research host, reported locally as macOS 27.0.1 / Darwin 27.0.0. This note interprets the supplied snapshot; it does not claim a new resource measurement or change any process. At that snapshot, `kern.memorystatus_vm_pressure_level` was 2, `memory_pressure -Q` reported 30%, wired pages were 1,517,658, compressor pages were 1,373,886, the page size was 16 KiB, and reported swap use was 14,034.56 MB. The experiment worker had exited. Public Apple source below is explanatory evidence, not a verified source checkout for this exact installed kernel build.

**Pressure 2 means warning.** The public pressure values are 1 normal, 2 warning and 4 critical. They differ from internal kernel enum numbers: reading an internal enum in isolation can incorrectly label the sysctl value 2 as “urgent.” Apple's sysctl handler converts internal pressure through `convert_internal_pressure_level_to_dispatch_level()`. [Apple XNU conversion and sysctl handler](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c#L1651), [public pressure constants](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/event_private.h#L274).

**The reported 30% is not an unconditional allocation budget.** Apple's published `memory_pressure` implementation obtains its percentage through `memorystatus_get_level()`. XNU maintains that level as available pages divided by total pages; the published non-jetsam path uses non-compressed memory, which includes active, inactive, free and speculative pages. This differs from a count of wholly unused physical pages. Pressure also depends on compression/reclamation conditions and recovery thresholds, so a warning and a seemingly comfortable percentage can coexist. The percentage alone cannot show that loading another model will be safe. Apple's user-facing explanation likewise includes free memory, swap rate, wired memory and cached files when describing memory pressure. [Apple memory_pressure source](https://github.com/apple-oss-distributions/system_cmds/blob/system_cmds-854.40.2/memory_pressure.tproj/memory_pressure.c#L102), [XNU level computation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/vm/vm_pageout.c#L4380), [pressure calculation and hysteresis](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md), [Activity Monitor explanation](https://support.apple.com/guide/activity-monitor/view-memory-usage-actmntr1004/mac).

The supplied page counters correspond to approximately 23.16 GiB wired and 20.96 GiB occupied by the compressor. These are substantial memory commitments on a 64-GiB host. A single swap-used reading indicates retained swapped data, not the current swap rate; it cannot attribute pressure to a particular process. The snapshot is insufficient to assign the warning to the now-exited experiment worker. Process RSS, MLX active allocations and physical footprint also measure different things. XNU's physical-footprint accounting includes internal memory, internal compressed memory, I/O mappings, nonvolatile purgeable memory and page tables, with accounting adjustments; summing convenient process or allocator counters is not a replacement for that accounting. [XNU physical-footprint definition](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task.c#L1139).

The legitimate controls available to an owned MLX worker are narrower than “free system memory”:

- Release references to completed operation arrays and KV caches, finish the relevant asynchronous work, and clear that worker's unused allocator cache. `get_active_memory()` excludes the free cache; `get_cache_memory()` measures buffers retained for reuse. `clear_cache()` releases unused cache allocations, not active model weights. [Active allocations](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.get_active_memory.html), [free cache](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.get_cache_memory.html), [clear cache](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.clear_cache.html).
- Set a smaller free-cache limit before operations and record active, cached and peak allocation values around them. This limits allocator retention; it is not a hard cap on process RAM or total host memory, and cache excess can be reclaimed on a subsequent allocation. [Cache limit](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_cache_limit.html), [MLX 0.32.4 Metal allocator](https://github.com/ml-explore/mlx/blob/v0.32.4/mlx/backend/metal/allocator.cpp).
- Do not treat MLX's memory limit or Metal's recommended working-set size as extra available RAM. MLX documents the memory limit as a guideline rather than a hard limit. Wired-limit control concerns residency and does not release live arrays. This worker's manual generation path does not use the separate `mlx_lm.generate.wired_limit` context; its presence elsewhere in the installed library is not evidence that this worker wired that amount. [Memory limit](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html), [wired limit](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_wired_limit.html), [Metal recommended working set](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize).

Starting a new Python process merely to call `mx.clear_cache()` cannot clear the allocator of a worker that has already exited. The useful prospective change is a smaller retained cache within the owned worker and explicit release/accounting between operations. Reusing one admitted model across isolated conditions can avoid repeated model loading, but the model remains resident and the host can still become unsuitable. The experiment therefore still needs its declared admission and resident-worker stopping rules. Nothing here justifies system purges, modifying other processes, or interpreting resource readiness as evidence about journal quality or internal experience.
