# Prospective owned process-interruption case

**Not executed by this document.** This is a separate recovery case after the selected uninterrupted minimized run has met its own finish line. Root controls the exact owned application and synthetic fixture. Neither global host sleep nor any Being process/service belongs to this case. A forced interruption cannot be counted as uninterrupted minimized duration.

## Identity and preselected finish line

Use the exact package SHA-256/PID/process-start identity from the selected run, and name the app-owned test session/store path. Preserve existing qualification folders and older session/export bytes. Prefer a separate named synthetic session if the endurance session has exhausted a configured budget: restoration must not replenish its step, attempt, duration or storage budget.

The primary question is whether an abrupt process death during an independently witnessed provider request preserves the last committed state without automatic resend or accepting a late response from the dead process. A second, optional case examines a separately witnessed saved Prepared boundary. Power-loss durability remains outside both cases because SIGKILL leaves the filesystem/kernel running.

## Held-request crash

1. Hold one response using the owned fixture and record its exact request number, body/prompt SHA-256, endpoint/model, receive time and accepted session/attempt/observation identity. The fixture's request log independently proves physical dispatch; a pre-dispatch checkpoint by itself cannot do so.
2. Copy the last committed manifest and its addressed checkpoint into a new evidence directory, record hashes and a segment/journal inventory, and retain the fixture-log prefix. Record the displayed numerical step separately from the durable step. Do not restore or edit the owned store.
3. Reconfirm the exact app PID/start/executable identity immediately before sending SIGKILL to that one process. Record wall and monotonic action times, return status and confirmed process absence. Ordinary Quit, SIGTERM handled gracefully, or SIGSTOP is not this trigger.
4. Release the old held fixture response after process absence. Record its handler completion as completion, not proof of client acceptance. Preserve all log rows, including client-disconnect evidence when present.
5. Relaunch the unchanged package against the same owned store. Observe an idle interval before restoration and establish that the fixture request count did not increase and no numerical step advanced. Recovery catalog metadata alone is not history verification.
6. Inspect/verify the selected retained chain, then Restore explicitly. Expect a held interrupted/blocked opportunity, the same durable state/RNG/covariance/controller/memory prefix, and no automatic resend. Preserve any uncommitted-object diagnostics. Do not infer recovery of unsaved visible frames.
7. Choose exactly one explicit decision: Skip the abandoned attempt then Start, or Retry with a new attempt ID. For Retry, retain request N+1 and its exact prompt/observation/memory association. Attempt N must remain interrupted; its late handler completion cannot create a journal or feedback application.
8. Await actual journal write/readback and durable Prepared checkpoint for the accepted new attempt, then allow one next numerical step. Export into a new destination through the native dialog and replay with the pinned executable. Compare the exact committed segment prefix to the pre-crash capture; require no journal for abandoned N and exactly one first-application event for any accepted replacement.

## Optional saved-Prepared crash

Use a separate witnessed boundary whose journal file has passed readback and whose manifest/checkpoint has committed Prepared feedback while paused. Preserve the journal ID/hash, prepared vector/intended next step and manifest/checkpoint bytes. SIGKILL the exact owned app, confirm absence, and relaunch unchanged. There must be no provider request or numerical advancement merely from launch/inspection/Restore. Explicit Start may apply that retained feedback once at its intended next step. Verify the extended chain and inspect a later held-vector step to distinguish first application from continued use.

## Interpretation and load

Retain action/result timestamps, source identities, immutable exports and verifier stdout. Label each planned case passed, failed, incomplete or unexecuted. Record compile/test/verification intervals separately from steady-run CPU/RSS windows; do not convert process CPU into system energy. A successful synthetic recovery case qualifies those states on this host/package only. It does not establish 24-hour operation, physical power-loss recovery, real-model reliability, other platforms or behavior of Astrid/Minime.
